# Reification Gradient

Does an LLM treat an *invented* diagnostic category as increasingly real as the **authority**
of its source rises — and does it *fabricate* clinical structure it was never given? A controlled,
synthetic-only, **preregistered** test of the clinician half of Ian Hacking's looping effect
(model-as-diagnostician).

The fabricated category is **disprosexia narrativa** (DN): a deliberately minimal name + one-line
gloss, with no committed symptom list. Descriptive content is held **byte-identical** across five
legitimacy levels (L1 forum → L5 pseudo-DSM); only the *authority wrapper* escalates. What we measure
is whether the model invents structure (criteria, treatments, differentials) it was never given, and
whether that fabrication scales with authority.

> **Preregistered outcome (Phase 6, `prereg-v1` + amendments A1–A4).** On the single validated
> confirmatory DV (`diagnosis`), the prespecified directional tests for **H1** (dose-response),
> **H2** (plausibility gating), and **H3** (anchor ceiling) were **not** supported; **H4** (the
> "invented for a study" flag lowers uptake) **was** supported. The observed cross-family ordering
> was `real_anchor < incoherent < DN_flagged < DN_plausible` — the *opposite* of the predicted
> authority ordering. This is a clean, preregistered result; see [`phase6/RESULTS.md`](phase6/RESULTS.md).
> `criteria_invented` was downgraded to **exploratory** (amendment A4) after it failed reliability.

Start here: **[`CLAUDE.md`](CLAUDE.md)** (invariants) → **[`PLAN.md`](PLAN.md)** (preregistration) →
**[`RUNBOOK.md`](RUNBOOK.md)** (how to run, phase by phase).

## Reading order of the preregistration

The preregistration is not a single file — it is a frozen core plus dated, additive amendments and
the pre-data evidence that justifies each sealed choice. Read in this order:

1. **[`CLAUDE.md`](CLAUDE.md)** — the anti-circularity invariants. The one thing that can kill the
   study is symptom content leaking into the seed. Read the invariants before anything else so the
   rest makes sense.
2. **[`PLAN.md`](PLAN.md) §1–§8** — the frozen preregistration: design, variables, hypotheses
   H1–H5 with falsification criteria, analysis plan, stopping rule. This is the sealed text; read
   the *exact* frozen version with `git show prereg-v1:PLAN.md`.
3. **Pre-freeze evidence PLAN.md relies on** (all dated *pre-data, pre-freeze*):
   - [`phase2/power_analysis/POWER.md`](phase2/power_analysis/POWER.md) then
     [`POWER_R0b.md`](phase2/power_analysis/POWER_R0b.md) → the N=60 / R=3 decision.
   - [`phase2/power_analysis/CONTEXT_BUDGET.md`](phase2/power_analysis/CONTEXT_BUDGET.md) →
     `num_ctx=2048`.
   - [`phase2/recognition_probe/RECODE_LOG.md`](phase2/recognition_probe/RECODE_LOG.md) → the
     real-anchor choice (**DPDR**), and [`MODELS.md`](phase2/recognition_probe/MODELS.md) → the
     sha256-pinned model digests.
4. **[`PLAN.md`](PLAN.md) §9 — amendments A1–A4**, in date order (all post-freeze but
   **pre-analysis**, additive, never editing a sealed decision):
   - **A1** — judge = `gemma2:27b` (names the previously-unspecified judge).
   - **A2** — human validation → directed audit (n=48) + supplementary co-rater (`phi4:14b`).
   - **A3** — `criteria_invented` v2 instrument + hardened success criterion.
   - **A4** — `criteria_invented` downgraded to **exploratory** after A3 re-validation failed.
   Supporting: [`phase4/validation/ALPHA_PREDICTIONS.md`](phase4/validation/ALPHA_PREDICTIONS.md)
   (dated predictions, made before validation) and
   [`AGREEMENT_RESULTS.md`](phase4/validation/AGREEMENT_RESULTS.md).
5. **[`phase6/RESULTS.md`](phase6/RESULTS.md)** — only after the above, so each number can be read
   against the sealed decision it tests.

## Verifying the chain of custody, step by step

Every step below is checkable from a clone. Run from the repo root.

**1 — Anti-circularity gate passes.** The seeds are minimal and the descriptive payload is identical
across L1–L5 (only wrappers differ). If this fails, the whole result is void.

```bash
python src/check_invariants.py        # expect: All hard invariants pass
```

**2 — The preregistration was frozen *before* the data existed.** The tag `prereg-v1` must be an
ancestor of the confirmatory-data commit, and dated earlier.

```bash
git show prereg-v1:PLAN.md | head -40                       # the sealed prereg text
git log -1 --format='prereg-v1  %h  %ci  %s' prereg-v1^{commit}
git log -1 --format='data       %h  %ci  %s' 770fa9c        # confirmatory run commit
git merge-base --is-ancestor prereg-v1 770fa9c && echo "OK: prereg precedes data"
```
Expected: `prereg-v1` = commit `4b2464f` (2026-07-13); confirmatory data `770fa9c` (2026-07-14) —
freeze precedes data.

**3 — Model weights are pinned by digest, not by moving tag.** Ollama tags are mutable pointers; the
sha256 digest is the real weight hash. Before trusting a replication, confirm your server's digests
match those recorded.

```bash
grep -nE 'digest|sha256' phase2/recognition_probe/MODELS.md
# generators mistral-small3.1:24b / qwen2.5:32b, judge gemma2:27b, co-rater phi4:14b
# cross-check against your own:  GET <OLLAMA_BASE_URL>/api/tags  (digest field)
```
`phase6/RESULTS.md` §4 records the digests were identical pre/post run (generators) and pre/post
scoring (judge).

**4 — The judge is sealed and blind.** The scoring model receives only two things: the **aliased seed
payload** and the **aliased response** — never the legitimacy wrapper, level, disorder type, or the
category's real/fictional name (the category name is replaced by `"LA CATEGORÍA"` in both). Read the
blinding contract and confirm `src/score.py` assembles the prompt from those two placeholders only.

```bash
sed -n '/## Blinding contract/,/emergent_symptom_tokens/p' scoring/judge_prompt.md   # what must NOT reach the judge
grep -nE 'BLINDED|LA CATEGORÍA|never the legitimacy|SEED_PAYLOAD|RESPONSE' src/score.py
```
The tokens `L1–L5` / `DN_plausible` etc. appear in `judge_prompt.md` **only inside the blinding
contract that forbids them** — not in the assembled prompt. The prompt template itself contains just
`{{SEED_PAYLOAD}}` and `{{RESPONSE}}`.

**5 — The validation set stayed sealed until human ratings were in.** The blind-id → cell mapping and
the judge/co-rater scores are sealed, with sampling seeds recorded; they are opened only after the
human `ratings.csv` is delivered (seeing a response's condition would bias the remaining ratings).

```bash
ls phase4/validation/SEALED_*                                # mapping + judge + co-rater, all sealed
grep -nE 'semilla|seed|SEALED|No abrir|hasta entregar' phase4/validation/README.md
```

**6 — Amendments are additive and pre-analysis.** A1–A4 live in `PLAN.md §9`, each dated, none edits
a sealed decision. A4 in particular was recorded *before any confirmatory aggregate was computed*.

```bash
sed -n '/## 9. Amendments/,$p' PLAN.md | grep -nE '### A[1-4]|2026-07'
```

**7 — Results are provenance-stamped.** `phase6/RESULTS.md` pins the prereg tag, the data commit, and
the scoring commit, and lists every seed in its reproducibility appendix (§4).

```bash
grep -nE 'prereg-v1|4b2464f|770fa9c|c4a5ce8|Semillas|digest' phase6/RESULTS.md
```

**8 — History-rewrite integrity (dead-hash sweep).** After the history rewrite, no retired
(pre-rewrite) commit hash should remain anywhere in the tree, and every short hash still referenced in
prose should resolve to a real object. The retired short-hash list is intentionally **not** inlined
here — writing those strings back into a tracked file would defeat the very sweep it documents. Run it
with the list your rewrite retired (expected matches: **0**):

```bash
grep -rInE '<retired-hash-1>|<retired-hash-2>|...|<retired-hash-6>' \
  --exclude-dir=.git --exclude-dir=.venv .          # expect: no output (zero matches)
```

This sweep was last run over the full tree with **zero** matches. Conversely, every *live* short hash
referenced in the docs (e.g. `4b2464f`, `770fa9c`, `c4a5ce8`) still resolves — check any one with
`git cat-file -t <hash>` (→ `commit`).

## Reproducing the run

Full operator walkthrough (what you do vs. what the code does, and the locks you must not delegate)
is in **[`RUNBOOK.md`](RUNBOOK.md)**. The exact command sequence for the confirmatory run and analysis
is in [`phase6/RESULTS.md`](phase6/RESULTS.md) §4. In brief:

```bash
pip install -r requirements.txt
python src/check_invariants.py                            # gate (must pass)
python src/run_batch.py --config config_tirada_real.yaml  # confirmatory run (7,200 calls)
python phase6/score_full.py --model ollama_remote/gemma2:27b   # blinded judge scoring
python phase6/analyze_confirmatory.py                     # the 4 primary tests
```

Two open-weight generator families run locally (mistral-small3.1:24b, qwen2.5:32b) via an Ollama
endpoint declared in `.env` (not versioned; see `.env.example`).

## Ethics & scope

Synthetic-only, sandbox-only. The fabricated category and all synthetic disorder content exist for
controlled in-silico measurement and **never leave this repo** as real clinical claims (`PLAN.md` §7,
`CLAUDE.md`). If it needs invented criteria to be diagnosed, that *is* the finding.
